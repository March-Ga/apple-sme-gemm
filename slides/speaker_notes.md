# Speaker notes

The slide titles, diagrams, and chart assets are generated by `build_slides.py`.
All performance figures use the saved run; no new benchmark is executed.

## 01. From outer products to competitive GEMM

Audience: programmers familiar with loops and matrix multiplication; no SME knowledge assumed. Allow about 25 minutes. The optimized implementation was measured against the original SME32 implementation and Apple's Accelerate library. All charts use the bundled full run, not estimated peak numbers. The central lesson is to optimize operand delivery, packing, compiler output and blocking together.

## 02. SME is an instruction set; Accelerate is a library

SME means Scalable Matrix Extension, not scalable extendable matrices. It is an Arm architectural extension exposed through machine instructions and C intrinsics. Accelerate is Apple's framework, including the BLAS interface used here. Apple documents runtime selection of processor-appropriate instructions; this experiment does not inspect the internal cblas_sgemm instruction path. Therefore Accelerate is a vendor library reference, not an SME-disabled control. [1] https://arm-software.github.io/acle/main/acle.html [3] https://developer.apple.com/accelerate/

## 03. One outer product updates many output values

Walk through one k value. Select a column of A and a row of B. Multiply each selected A value by each selected B value: a two-element column times a three-element row creates a 2×3 update. Add that update to C. Repeat for every k to obtain the full matrix product. FMOPA carries out a predicated outer-product accumulate into ZA; it does not complete an arbitrary N×N GEMM in one instruction. Example arithmetic is exact integer arithmetic shown as a teaching aid. [1] https://arm-software.github.io/acle/main/acle.html [2] https://scalable.uni-jena.de/opt/sme/micro.html

## 04. ZA holds four logical FP32 tiles on this M4 Pro

This implementation checks the streaming vector length at runtime and requires 16 FP32 lanes, equivalent to 512 bits. With a 64-byte SVL, total ZA storage is 64×64 bytes = 4096 bytes. In the FP32 view this is four 16×16 tiles, each holding 256 floats or 1024 bytes. The colored boxes are logical tile views; do not interpret their placement as physical SRAM geometry. Predicates select active lanes. Our dimensions are multiples of 32, so full-lane predicates are used. [1] https://arm-software.github.io/acle/main/acle.html [2] https://scalable.uni-jena.de/opt/sme/micro.html

## 05. Streaming mode surrounds the complete kernel

The public computation functions use __arm_locally_streaming with __arm_new("za"). The compiler handles the body entering and leaving streaming mode and creates fresh zero-initialized ZA state according to ACLE. The kernel explicitly resets ZA for each new output tile; subsequent K blocks reload previous C. Internal helpers declare __arm_streaming __arm_inout("za") to share the caller's ZA. This keeps transitions outside the inner tile helper loop. A packing call using ZA has its own function boundary, and total timings include it. The pseudocode omits details of all four tile updates. [1] https://arm-software.github.io/acle/main/acle.html

## 06. The 32×32 baseline already uses all four ZA tiles

Original SME32 is our project baseline, not an official standard or a scalar implementation. A0 and A1 contain two adjacent groups of 16 output rows. B0 and B1 contain two groups of 16 output columns. The four outer products form the quadrants of one 32×32 output tile. Both inputs are packed into 16-lane panels before compute. K is blocked into groups of 256; later groups reload the current C tile and continue accumulating. The baseline already uses four ZA tiles, so the optimization cannot be described as merely enabling all tiles.

## 07. Compare the same operation and timing boundary

All implementations compute C=A×B with FP32 row-major inputs, alpha=1 and beta=0. One calling thread is used; Accelerate BLAS is explicitly forced to single-thread execution and checked. Dimensions are 32,64,128,256,512,1024,2048,4096. Each of three randomized rounds collects seven batch-average samples per case, with calibration targeting at least 30 ms per sample. Inputs are reused and allocation, initialization, process startup, calibration and verification are excluded. Compute mode includes arithmetic and all C traffic but starts with prepared inputs. Accelerate is total-only because its internal packing cannot be exposed separately. Speedups are ratios of within-round medians, summarized across rounds; IQR is not a confidence interval. The run is a steady-state single-calling-thread measurement, not cold-cache latency or chip-wide throughput. Power metadata reported AC Power; the battery line simultaneously reported discharging, so energy-mode or battery claims are not inferred. [4] https://developer.apple.com/documentation/accelerate/blas_threading_single_threaded

## 08. Original SME32 trails Accelerate end to end

Read the left chart as absolute throughput, where higher is better. Read the right chart as Accelerate time divided by original SME32 time, so values below one mean the original is slower. At N=4096, original SME32 delivers about 0.945 TFLOP/s versus 1.571 for Accelerate. The baseline gap is not proof that the SME instructions are slow: the next slide separates prepared-input and total timings. Shading is IQR of three paired-round ratios, not a confidence interval.

## 09. Small and large matrices reveal different costs

At N=128 the original and optimized compute medians are close, while total timing differs greatly. This points to the data-preparation path as the main opportunity at small sizes. At N=4096 the optimized implementation also improves prepared-input performance substantially, so the large-size result requires changes to the kernel, layout and blocking. Do not subtract these independent medians and call the difference an exact isolated packing measurement. Memory/cache state and separately collected timing variation make that interpretation too strong.

## 10. Use a size-specific path with an explicit fallback

The dispatcher requires supported dimensions: multiples of 32, from 32 to 8192. Through N=512 it transposes A using ZA and uses B directly in its original row-major layout, still computing 32×32 tiles. For larger sizes divisible by 64 it uses the 16×64 kernel with A16/B64 packing and larger blocking parameters. Larger dimensions not divisible by 64 use original packing and SME32. This is a transparent fallback without padding or hidden BLAS delegation. The full timing suite contains powers of two, so its larger cases all select the 16×64 path; the non-power-of-two fallback is covered by correctness tests rather than these throughput charts.

## 11. Transpose A inside ZA to build contiguous panels

The visual uses a 4×4 toy tile so every value can be followed. The actual packer processes 16×16 FP32 blocks. For each block, 16 row loads populate a ZA tile; groups of four vertical vectors are then read using svread_ver_za32_f32_vg4 and stored contiguously with svst1_f32_x4. The packed A panel places the 16 output-row values for a fixed k next to each other. The baseline uses NEON-based transpose/packing; this path uses SME's tile access to express the transpose directly. No arithmetic GEMM result is stored during packing. [1] https://arm-software.github.io/acle/main/acle.html

## 12. For small matrices, avoid packing B entirely

For the small path A still needs packing, now through the ZA transpose. B[k*N+j] is already the beginning of a contiguous group of 32 columns, so a two-vector load supplies B0 and B1 directly to the existing four-FMOPA 32×32 calculation. This eliminates the B preparation pass and keeps a full K sweep for each output tile. The choice is limited to N≤512 because avoiding packing at larger dimensions was not the winning measured strategy. Numbers here compare optimized against original, with total and compute speedups taken separately from speedups.csv. Since packing is excluded in compute, the large total gains paired with near-one compute gains support the small-size diagnosis without pretending to be an isolated packing ablation.

## 13. Reshape the large-matrix kernel to 16×64

All four logical 16×16 ZA tiles are arranged across one 16×64 output tile. One 16-lane A vector is reused with each of four consecutive B vectors loaded by svld1_f32_x4. Both shapes perform four FMOPA operations and 2048 nominal FLOPs per k. The new shape actually reads five logical operand vectors per k, versus four in the original 32×32 kernel: 320 versus 256 bytes, ignoring C traffic and cache reuse. Its benefit must therefore be evaluated jointly with grouped loads, panel layout, scheduling and blocking; it is not a reduction in raw operand bytes. The wider logical shape is a design for this implementation, not an architectural requirement.

## 14. Keep the loaded tuple local to each K iteration

During tuning with Apple Clang 17, carrying the four-vector B tuple across K iterations caused five additional streaming-vector register copies per k. This observation is recorded in the current source comment; the earlier experimental disassembly and paired measurements were not retained in the final repository. Therefore this slide gives no invented speedup or counter measurement for that rejected variant. The final loop loads A and a local B tuple, consumes them immediately, and is unrolled by four. Build auditing verifies FMOPA uses four tiles and that grouped vector loads are present. Those structural checks do not constitute a general proof that any compiler emits zero register moves.

## 15. Use larger K blocks and bounded M/N traversal

The actual nesting is pc (K), jc (N), ic (M), j (64 columns), i (16 rows). For a full macroblock, A spans 256×2048 floats = 2 MiB; B spans 2048×512 floats = 4 MiB. These are logical panel footprints, not measured cache residency, and additional C and buffers exist. At N=4096 the original K=256 scheme makes sixteen K passes per output tile, whereas K=2048 needs two. The first pass starts from zero and later passes reload C. This changes logical C load/store frequency: sixteen stores/fifteen reloads versus two stores/one reload per element across the complete product. It does not imply an eightfold reduction in DRAM traffic or an eightfold runtime gain. Blocking values were selected empirically for this M4 Pro/compiler, not claimed universal.

## 16. Tile B packing so source and destination stay local

The full B64 packing loop is pc, jc stepping by 256 columns, kk stepping by 32 K rows, k, j stepping by 64, then four 16-float NEON load/store groups. A chunk covers 32×256×4=32768 bytes of logical source values. Four adjacent 64-column panels are filled over those 32 rows before moving on. The four-vector FP32 load in the compute kernel can then fetch one contiguous 64-value B row from a packed micro-panel. These NEON packing groups should not be confused with the SME2 four-vector loads in the streaming compute function. Packing remains part of total timing. The chosen packing and compute blocking constants are different: 256 packing columns versus NC=512 compute columns.

## 17. The optimized version closes most of the library gap

All three curves are generated directly from summary.csv. Each throughput value is 2*N^3 divided by the pooled median time, expressed in TFLOP/s. At N=512 the optimized and Accelerate curves are almost identical. At N=2048 the optimized implementation remains slower. At N=4096 both are around 1.57 TFLOP/s, while original SME32 is about 0.945. Do not claim the optimized version universally beats Accelerate, or that these results show all-chip peak throughput.

## 18. Against Accelerate: small-size wins, large-size parity

Ratios come from speedups.csv: medians of within-round timing ratios, with IQR across three rounds. This is why they can differ slightly from ratios of the throughput values or pooled medians. At N=32 the paired optimized speedup is about 2.69×, but absolute batch-average calls are sub-microsecond, so do not generalize this to tail latency. At 4096 the optimized/Accelerate ratio is about 1.006× with IQR crossing 1, which is effectively parity for interpretation. At 2048 it is 0.946×, equivalent to about 5.7% longer runtime because inverse speedup minus one is the slowdown. A few percent elsewhere should be read with variability in mind.

## 19. The optimized path improves preparation and compute

Pink includes packing and blue excludes it. At N=128 total improves by about 2.40× while compute improves only about 1.03×, consistent with preparation being the main small-size opportunity. At N=4096 total improves by about 1.67× and compute by about 1.64×, consistent with the large-path design also improving arithmetic/data delivery. These before/after comparisons combine several changes; no per-optimization causal speedup or ablation is claimed. The K-block count and logical panel sizes explain plausible mechanisms, while the measured curves are the end-to-end evidence.

## 21. Keep correctness, generated code, and timing together

The repository checks packing and GEMM with AddressSanitizer and UndefinedBehaviorSanitizer, a scalar double reference, multiple sizes/seeds and output guards. Benchmark jobs perform numerical checks before and after sampling, including a finiteness scan. Build manifests record source and binary hashes, compiler flags and disassembly properties. The runner rejects a source/binary mismatch. Limitations: FP32 only, square multiples of32 only, warm reused inputs, one calling thread without guaranteed CPU affinity, no energy or multicore results, and no isolated SME-versus-NEON experiment. To study pure ISA uplift one would need a controlled no-SME implementation and comparable packing, blocking, compiler and arithmetic semantics. The current result is useful as an implementation comparison. Slides can be rebuilt from saved results without running GEMM.
